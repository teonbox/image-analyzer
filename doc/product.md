# 产品需求文档：基于 AWS Bedrock 的批量图像分析系统

## 一、产品概述

本系统旨在构建一个基于 AWS Bedrock 模型的批量图像分析解决方案，主要用于处理从视频中连续捕获的图像帧。系统采用异步处理架构，支持多种分析策略，能够处理大规模图像批次，并在完成后通过回调机制通知调用方。

系统的核心价值在于提供灵活的图像分析能力，允许开发者根据不同的业务场景实现多种分析策略，同时系统底层负责处理任务调度、错误重试等复杂性。系统采用批次化处理模式，将大规模视频帧拆分为多个批次独立处理，每个批次包含核心帧和上下文缓冲帧，确保分析时能够访问前后帧作为参考。

## 二、业务场景

系统处理的图像来源于视频捕获工具，这些工具会按照一定的时间间隔从视频中提取图像帧。每个文件夹代表一个视频源，文件夹内的所有图像共享相同的前缀，并以数字作为后缀进行编号。图像的命名格式可能是 xxx-001 或 xxx-1 这样的形式，其中数字通常与视频的时间轴相关，但具体的采样间隔由捕获工具决定。系统需要能够自动识别图像的命名规则和前缀模式，如果检测到多个不同的命名模式，系统将返回错误响应。

由于视频捕获过程中可能存在丢帧情况，系统需要具备容错能力，能够处理不连续的图像序列。典型的视频时长从1小时到3小时不等，对应3600到10800张图像帧，超过6小时的视频不是典型场景。系统设计需要充分考虑这种大规模数据处理的需求。

## 三、功能需求

### 3.1 请求提交

系统提供接口接收图像分析请求，支持两种输入方式。第一种是提供存储桶信息（如 OSS、S3 等），系统会自动加载指定文件夹下的所有图像。如果列出图像超过 30 秒，系统将返回错误，用户可选择使用第二种方式。第二种是直接提供图像 URL 列表。

用户提交请求时需要提供名称字段用于标识和追踪任务，以及回调地址用于接收完成通知。接口使用 API Key 进行认证。接口在接收到请求后应尽快响应（理想情况下 1 秒内），返回请求 ID 供后续查询使用。

### 3.2 进度查询

系统提供查询接口，支持通过请求 ID 或名称查询任务状态和进度。当使用名称查询时，如果存在多个同名请求，系统返回最新的一个，并在响应中提示存在多个匹配项。

查询接口返回任务的总帧数、已完成数、失败数、待处理数等统计信息，用户可据此计算完成百分比、错误率和成功率。任务状态包括：
- pending：刚创建
- running：处理中
- partial_complete：部分帧成功部分失败
- partial_failed：无成功帧但有失败帧
- completed：所有帧成功
- failed：所有帧失败

### 3.3 结果获取

系统提供结果获取接口，返回完整的分析结果。完整结果以 JSON 文件形式存储，接口返回存储位置信息和预签名 URL（1天有效期）。每次调用此接口都会生成新的预签名 URL，建议用户使用存储位置信息直接访问以获得长期有效性。

### 3.4 分析策略

系统支持多种分析策略，每种策略代表一种特定的图像分析方法。策略在部署时配置，最多支持 20 个策略。不同的分析策略具有不同的处理模式。

第一种模式是逐帧分析，策略会按顺序处理每一张图像。这种模式适合需要对每一帧都进行分析的场景，比如需要完整记录视频中每一个时刻的状态变化。第二种模式是间隔采样分析，策略可以根据自身需求跳过某些图像，只处理特定间隔的图像帧。这种模式可以降低处理成本，适合那些不需要逐帧分析的场景，比如每隔10帧采样一次就足够了。第三种模式是上下文关联分析，由于图像来源于视频，某些分析场景需要参考目标图像前后的帧来获得更好的理解效果。

对于上下文关联分析，系统为每张目标图像提供其前后一定范围内的参考帧，通常是前后各 60 帧。需要明确的是，分析的目标始终是单张图像，前后帧仅作为参考信息，具体是否使用、使用多少帧由策略自身决定。比如某个策略可能只需要前后各1帧就够了，而另一个策略可能需要前后各30帧。系统会把这些参考帧的信息都提供给策略，策略自己选择使用哪些。

策略的分析结果采用 key-value 格式，所有策略的结果合并存储在一起。不同策略应该使用不同的 key 来避免冲突，比如策略A使用 detection_result 这个 key，策略B使用 classification_result 这个 key。如果两个策略使用了相同的 key，后面的策略会覆盖前面策略的结果，这种情况被视为策略开发时的错误。系统会记录每个策略对每个帧的执行状态，包括已完成、已跳过、失败等状态，这样用户可以清楚地知道哪些策略处理了哪些帧。

作为一个具体的例子，我们来看看喝东西检测这个策略。这是一个典型的图片打标需求，需要判断视频帧中的人物是否正在喝东西。这个需求看起来简单，但实际上有一定的复杂性。如果只看单张图片，很难准确判断一个人是不是在喝东西。比如一个人拿着杯子或瓶子，但他可能只是在介绍这个饮品，或者在展示产品，并没有真正在喝。又或者他只是把杯子举到嘴边准备喝，但还没有开始喝。我们需要打标的是"正在喝"这个动作，而不是"拿着饮品"这个状态。

为了提高判断的准确性，这个策略会使用连续的几张图片来进行分析。具体来说，每次分析时会使用3张图片，包括目标帧本身，以及它前面1帧和后面1帧。通过观察这3张连续的图片，可以看到动作的变化过程。比如前一帧中杯子在桌上，目标帧中杯子在手上移动向嘴部，后一帧中杯子贴近嘴部并倾斜，这样的连续动作就能更准确地判断出这个人正在喝东西。相反，如果3张图片中杯子的位置都没有变化，只是拿在手上，那就说明这个人可能只是在展示饮品，而不是在喝。

这个策略使用 AWS Bedrock 的 Nova Lite 模型来进行分析。模型会综合考虑多个因素，包括人物的手部动作、嘴部动作、杯子的位置变化、倾斜角度等等。通过这些连续帧的信息，模型可以更准确地区分"正在喝"和"拿着饮品"这两种情况。

分析完成后，策略会返回几个关键信息。首先是一个布尔值，表示目标帧中的人物是否正在喝东西。其次是一个置信度分数，范围从0到1，表示这个判断的可信程度。最后还会有一段简短的文字描述，说明具体观察到的情况，比如"人物正在将杯子倾斜送入口中饮用"或者"人物只是拿着杯子在讲解，并未饮用"。这个描述可以帮助用户理解为什么会得出这样的判断结果。

这些结果信息会以特定的 key 存储，所有的 key 都以 drinking_ 开头，比如 drinking_is_drinking、drinking_confidence、drinking_details。这样的命名方式可以确保不会和其他策略的结果发生冲突。如果同一个请求中还配置了其他策略，比如人脸识别策略，那么最终的结果中会同时包含喝东西检测的结果和人脸识别的结果，它们通过不同的 key 区分开来。

### 3.5 完成通知

当所有图像的分析任务全部完成或超时时，系统向回调地址发送通知。回调请求包含请求 ID、名称、状态、统计信息、存储位置、预签名 URL 以及过期时间提示。

考虑到网络的不稳定性，回调机制具备重试能力。回调失败时按照配置的延迟策略进行重试（如立即、1分钟后、5分钟后、30分钟后、1小时后），达到最大重试次数后标记回调失败。回调状态独立管理，包括 pending、success、failed、retrying 等状态。

### 3.6 容错与重试

系统具备完善的容错机制。对于单个图像的分析失败，系统会进行延迟重试，重试失败后标记该图像为错误状态，继续分析其他图像。对于批次处理失败，系统会重试整个批次，如果能够保存已完成图像的状态，则跳过这些图像。

系统设置超时限制（默认 2 小时），定期检查运行中的任务。超时的任务会被强制标记为完成状态，未完成的图像标记为失败，但保留已有的部分结果。系统会触发完成通知，结果中包含失败的图像信息。

### 3.7 批次处理

由于单个视频可能包含数千张图像，系统采用批次化处理策略。批次大小根据策略数量动态计算，用户可以通过系数参数调整批次大小。每个批次包含核心帧（需要输出分析结果）和缓冲帧（仅作为上下文参考）。

批次之间可以并发处理，并发度可配置。系统确保即使某些批次失败，其他批次仍能继续处理。批次处理失败时会进行重试，如果能够保存单个图像的处理状态，重试时会跳过已完成的图像。

## 四、问题与解答

[Q] 系统是否需要支持实时查询任务进度的 API，还是仅通过回调通知最终结果？
[A] 需要提供 API 来查询进度。

[Q] 对于上下文关联分析，前后参考帧的范围是固定的（如固定 10 秒），还是应该作为策略的可配置参数？
[A] 固定的，如何使用、使用多少由策略自己决定。

[Q] 分析结果的存储方式是什么？是存储在数据库中供后续查询，还是仅在回调时传递？
[A] 存储在数据库中。

[Q] 当部分图像分析失败时，任务的整体状态应该如何定义？是标记为部分成功，还是整体失败？
[A] 整体状态有 pending、partial complete、partial failed、failed、complete。

[Q] 系统是否需要支持任务的取消操作？如果需要，已经在执行中的分析任务如何处理？
[A] 不需要。

[Q] 图像的前缀自动识别逻辑，是否需要支持多种命名模式，还是假设同一批次内的图像命名规则一致？
[A] 自动识别。如果有多个模式，返回错误响应。

[Q] 回调重试的策略参数（如最大重试次数、重试间隔）是全局配置还是可以在 API 调用时指定？
[A] 全局配置。

[Q] 不同分析策略的结果格式是否需要统一，还是允许每个策略返回自定义的结果结构？
[A] key-value 结果，合并在一起，不需要关心覆盖问题。

[Q] 系统是否需要提供分析策略的注册和管理机制，还是策略在部署时静态配置？
[A] 策略是代码，不是动态策略。部署时它们是固定的。

[Q] 对于大规模图像批次（如数千张图像），是否需要支持分批处理或流式处理，以避免单个任务执行时间过长？
[A] 是的，分批处理。

[Q] 一个请求对应一个文件夹（一个视频），还是可以包含多个文件夹（多个视频）？
[A] 当用户调用 API 时，用户提供存储信息或图片列表以及其他请求信息，这些都是关于一个视频的。但你需要知道，一个3小时的视频有10800张图片，这非常大。

[Q] 如果一个文件夹内有多个不同前缀的图片（多个视频混在一起），是分别处理还是报错？
[A] 返回错误消息，不处理。

[Q] 如果视频有几千张图片，处理时间可能很长，如何处理超长任务？
[A] 1小时的视频很常见，3小时的视频并不罕见，超过6小时的不是很典型。

[Q] 是否需要提供 API 查询单个帧的分析结果？如何识别一个请求？
[A] 是的，你需要一个 API 来获取请求的所有结果。你可以通过生成的 request_id 或用户传递的 name 来识别请求。通过 request_id 你可以查询结果，这很明显。通过 name，如果只存在一个具有该名称的请求，你可以查询结果。或者你可以查询具有相同名称的最新请求的结果。你应该响应一个属性来告诉有多个具有相同名称的请求，只是返回最新的一个，要求用户通过 id 查询。

[Q] 列出存储桶中的所有图片可能很慢（如 21600 帧），如果超过 30 秒超时怎么办？
[A] 不用关心，直接返回错误消息。用户可以自己解析图片链接。这是他们的选择。

[Q] 如果视频有 21600 帧，回调数据可能非常大（每帧结果 * 策略数）。是否需要分页回调，或者只在回调中提供摘要，详细结果通过 API 查询？
[A] 是的，你应该将最终结果整理成 JSON 并保存到存储中，当回调时，你只需给用户存储位置，附带一个 1 天过期的预签名 URL，并添加一个注释属性告诉过期时间，要求用户直接通过存储位置获取数据。

[Q] 关于预签名 URL 的刷新：预签名 URL 1天后过期。如果用户在过期后需要访问结果，是否需要提供 API 重新生成预签名 URL？还是要求用户使用存储位置直接访问？
[A] 当获取结果时（通过 GET result API），你再次获取预签名 URL。

[Q] 如果策略的 shouldProcess 返回 false 跳过某一帧，是否需要记录该策略跳过了这一帧？还是完全不记录？
[A] 好主意，你可以保存策略状态，哪个被使用，哪个被跳过。很好。

[Q] Request 的状态转换规则是什么？running -> completed 可以，running -> failed 可以（超时），那么 failed 可以转换为 completed 吗（如果重试后成功）？还是 failed 是终态？
[A] 如果所有帧都失败，请求标记为 failed。添加像 partial_complete、partial_failed 这样的状态。complete: 所有帧都成功。failed: 所有帧都失败。partial_complete: 当一些帧处于 pending 或 running 时，有一些成功帧和失败帧。partial_failed: 当一些帧处于 pending 或 running 时，没有成功帧但有失败帧。对于重试机制，第一次失败会标记帧为 failed，假设所有帧在第一次同时失败，此时请求状态为 failed。但在后续重试中，一些帧完成，所以请求状态变为 partial_complete。如果最终所有帧完成，请求状态变为 complete。

[Q] 如果完成结果聚合但回调失败，请求的状态应该是什么？是否需要单独的字段来跟踪回调状态？
[A] 需要单独的字段。

[Q] Request 创建后的初始状态是什么？pending 还是 running？什么时候从 pending 转为 running？
[A] Pending。当第一个帧开始处理时，变为 running。请在你的设计中描述状态转换。

[Q] partial_complete 和 partial_failed 什么时候转换为最终状态（complete 或 failed）？是在所有帧处理完成时自动转换，还是在超时强制转换？
[A] 两者都是。
