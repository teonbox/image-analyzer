# Q&A 问答记录

## Q1: 并发控制
[Q] Worker Lambda的并发数是指单个Lambda实例内的并发,还是整个系统的Lambda并发数限制?
[A] 如果使用 Lambda，并发数指的是并发 Lambda 实例数，单个 Lambda 实例内单线程运行业务逻辑。

## Q2: 结果存储
[Q] 分析结果是只存储在DynamoDB中,还是也需要存储到S3?
[A] 数据量不大，只是 JSON 结果，存储在 DynamoDB 中就足够了。

## Q3: SQS 消息粒度
[Q] 是每个 task 一条消息，还是每张图片一条消息？
[A] 是的，单个 Lambda 处理整个任务可能会超时。实际上，对于分析一张图片，它需要的一切就是它前后1分钟的内容，这是极限。你可以将所有相关数据传入 SQS 消息，这样每个消费者可以独立处理 SQS 消息而不需要顺序。

## Q4: 批次大小
[Q] BATCH_CORE_SIZE 默认600帧是否合适？
[A] 600 太大了。一次调用最多可能需要 10 秒，对于一张图片我们可能调用 10 次。我们需要考虑异常情况。如果发生错误，整个批次可能失败，下次你需要重试整个批次。600 对于一个批次来说太大了。

## Q5: 策略并行
[Q] 在单个批次内，多个策略是真正并行执行（多线程/多进程），还是顺序执行？
[A] 分别执行。你需要控制 Lambda worker 的并发。我认为一个 worker 同时只调用 Bedrock 一次，对吧？

## Q6: 批次失败
[Q] 如果某个批次的 Lambda 执行失败（如超时、内存不足），是否需要重试整个批次？
[A] 如果你有办法为每张图片保存状态，那很好，这样你可以跳过之前已完成的图片。如果没有，你需要重新处理批次中的所有图片。

## Q7: 成本优化
[Q] 对于间隔处理策略（如每10帧处理1帧），是否可以在批次划分时就跳过不需要的帧？
[A] 在你的框架中你不知道策略，策略是由开发者开发的，策略会一直变化。策略不是很多，最多 20 个，这是肯定的。

## Q8: Frame 表写入
[Q] 为每一帧创建 Frame 记录，21600 帧需要写入 21600 条记录。是否可以接受？
[A] Batch Processor 处理时才创建。

## Q9: 策略加载
[Q] ENABLED_POLICIES 配置的策略如何加载？是预先打包在 Lambda 中，还是动态加载？
[A] 预先打包在 Lambda 中。

## Q10: Bedrock 模型选择
[Q] 不同策略是否可以使用不同的 Bedrock 模型？
[A] 使用不同的 Bedrock 模型，那是策略中的代码，不是框架的事。你可以提供库供开发者在策略中使用。

## Q11: 批次并发控制
[Q] WORKER_CONCURRENCY=10 表示最多 10 个 Lambda 实例并发。如何确保不超过这个限制？
[A] 当然，你应该配置 SQS 的最大消费者数，这是限制并发的方式。

## 关键决策总结

| 问题 | 决策 |
|------|------|
| 并发控制 | 通过 SQS MaximumConcurrency 配置 |
| 消息粒度 | 每个 Frame 一条 SQS 消息 |
| 策略执行 | 顺序执行，不并行 |
| 结果存储 | DynamoDB + S3（完整结果） |
| 回调重试 | Lambda 内重试，每 30 秒一次，最多 5 次 |
| 超时处理 | Health Check 标记为完成，允许部分失败 |
| API 认证 | 使用 API Key |
| 预签名 URL | 1 天有效期，可配置 |
